\begin{abstract}
\noindent
\textbf{Mission.} Close the atmosphere half of the AWI-ESM3 $\leftrightarrow$ PISM cycle in both
directions: PISM's surface mass balance driven by the OIFS leg that just ran, and the ice-sheet
surface elevation OIFS runs with following the ice sheet PISM produced. The ocean half was closed
by the moving-cavity campaign; this is its companion.

\medskip\noindent
\textbf{Where we are.} The SMB direction is closed. OIFS's own $P-E-R$ reaches PISM and PISM
integrates on it, which retires the 130\,ka taint of \S\ref{sec:taint}: the paleo file was driving
the ice sheet 50\% too wet. The ice sheet's discharge reaches the ocean as icebergs and runs. The
concurrent chain works end to end, so the PISM decade runs inside the ocean year rather than after
it (\S\ref{sec:concurrent}). One blocker is live and intermittent: an OIFS overflow in
\code{EXP(LZ0H)} that has now killed a leg with nothing else wrong (\S\ref{sec:lz0h}). The
orography direction has not started.

\medskip\noindent
Timeline in \S\ref{sec:campaign}, current state and open items in \S\ref{sec:state}, dead claims
in \S\ref{sec:falsified}.
\end{abstract}

\section{The campaign, in the order it happened}
\label{sec:campaign}

\subsection{Taking stock: the atmosphere side is a stub (2026-08-03)}
\label{sec:taint}

\code{couplings/oifs/just\_copy\_stuff.functions} copies \code{atmosphere\_file\_for\_ice.nc}
verbatim out of \code{a270122/lars\_and\_paul/experiments/E130ka\_coupled3}. Confirmed in
\code{eval5}: a $192\times96$ ECHAM Gaussian grid carrying \code{temp2}, \code{tsurf},
\code{aprt}, \code{orog}, \code{swd}, \code{cc}, \code{q2m}, \code{tau}, \code{emiss},
\code{uv}, \code{TOAswd}.

\textcolor{red}{\textbf{TAINTED}}: every PISM leg of the moving-cavity campaign, \code{eval5} and
\code{fgdbg02} included, ran dEBM on a 130\,ka paleo ECHAM atmosphere. No PISM surface mass
balance number from that campaign is a statement about AWI-ESM3. Ocean-side results are not
affected; they are forced from FESOM output directly.

Two further findings from the same read. \code{suorog.F90:151--250} already implements both
returns: \code{ECE\_CPL\_ISMM} reads \code{usurf\_oifs} and patches \code{ZZOROG} through
\code{REESPE}/\code{SPEREE}, \code{ECE\_LANDICE} reads \code{plit\_oifs}. That code is upstream
(vendor \code{a2e46d5}, Jorge Bernales) and our \code{suorog.F90} is byte-identical to it. But we
run \code{ECE\_LANDICE} only, and the \code{plit} we write is not PISM's ice mask:
\code{make\_plit\_oifs.py} derives it from the regenerated ICMGG land--sea mask capped at
$60^\circ$S. \code{eval5/couple/antar\_pism2ece.nc} holds one variable, \code{plit\_oifs},
\code{nx}=40320. No \code{usurf\_oifs}. So no PISM geometry reaches the atmosphere at all.

\subsection{Choosing the ISM-mapper over XIOS (2026-08-03)}

Everything dEBM needs is already in the XIOS output, and the de-accumulation pattern exists in
\code{field\_def\_lpjg\_safe.xml.j2}. Checked against \code{eval5} year 1903: \code{ssrd}
$=6.845\times10^5$ and \code{tisr} $=1.226\times10^6$\,J\,m$^{-2}$ per one-hour step give 190 and
340\,W\,m$^{-2}$; \code{lsp+cp} $=1.13\times10^{-4}$\,m/step gives
$3.14\times10^{-5}$\,kg\,m$^{-2}$\,s$^{-1}$. All correct global means, so a jinja-gated
\code{file\_def} block would have delivered the forward direction with no new component.

Decided against it. XIOS solves the forward direction only: it cannot deliver \code{plit} into the
live atmosphere, and cannot route basal melt and discharge into the ocean. Both need a component
inside the OASIS exchange, and one mechanism is better than two. Staying on the EC-Earth component
also keeps CISSEMBEL available.

Also decided: carry both SMB schemes with dEBM as default; SMB before orography; everything behind
\code{general.smb\_coupled}.

\subsection{The ISM-mapper becomes an esm\_tools component (2026-08-03)}

\code{configs/components/ismm/ismm.yaml}, in the \code{develop-is} coupling, always built.

It is not a standalone repository: it lives inside \code{ecearth4} under
\code{sources/ism-mapper}, so the component clones ecearth4 and builds that subtree. The clone is
37\,MB, not the 663\,MB the local \code{.git} suggests, because every \code{sources/*} model is a
submodule that is not recursed into. The branch \code{cissembel-levante-intel} is required rather
than preferred: it carries \code{5799a2a}, which fixes an \code{EBMfinalize} use-after-free that
crashes any run with a non-CISSEMBEL region.

CISSEMBEL is a \emph{link-time} dependency even on the direct path
(\code{ism-mapper\_run\_mod.F90:7} has an unguarded \code{use modEBMworld}), so it is built from
the same clone. At runtime \code{EBMworld} only fires for regions with
\code{ISMRGNCIS(n)=.true.}, so it never executes for us.

The committed \code{Makefile} carries ECMWF HPC2020 paths. Everything it needs is a plain make
variable and command-line macros beat file assignments, so the machine configuration is passed in
\code{comp\_command} rather than by patching a tracked file.

\medskip\noindent
\textbf{Verified.} Built end to end from a fresh clone. The open risk was whether code written
against OASIS 5.2 links against our 5.0-smhi; it does, with no source change. The binary carries
\code{oasis\_init\_comp}, \code{oasis\_def\_var}, \code{oasis\_enddef}, \code{ebmworld} and
\code{ebminitialize}.

\subsection{The PISM grid goes into ocp-tool (2026-08-03)}
\label{sec:grid}

The ISM-mapper is an OASIS component, so the PISM domain must appear in
\code{grids.nc}/\code{masks.nc}/\code{areas.nc}. This went into ocp-tool, not esm\_tools: ocp-tool
already sits between PISM and AWI-ESM3, it is where the weight generation lives, and
\code{ocp\_tool/grids/} already has the abstraction (a class with \code{cell\_latitudes},
\code{cell\_longitudes}, \code{cell\_corners}, \code{cell\_areas}, \code{cell\_masks}). Putting it
there deleted a planned step: ocp-tool writes \code{ismp} itself, so nothing appends fragments
afterwards.

Centres come from the PISM file's own \code{lat}/\code{lon}; corners are inverse-projected from the
cell corner $(x,y)$; areas are spherical excess over two triangles.

\medskip\noindent
\textbf{Verified} on \code{antarct\_cr} 8\,km, $761\times761$, three ways, because a wrong grid
fails as silently-bad weights rather than a crash:
\begin{itemize}
\item Area total 36.03 against 36.28\,$\times10^6$\,km$^2$ from the plane area corrected by the
      polar stereographic scale factor, $-0.70\%$.
\item Cell areas 67.0\,km$^2$ at the pole to 53.8 at the outer corner against a nominal 64, the
      right sign and size for \code{lat\_ts}$=-71$.
\item All 579121 cells wind counterclockwise seen from outside the sphere, no sign flips. SCRIP
      requires this and the area check cannot detect it.
\end{itemize}
A full TCO95/CORE3 run puts \code{ismp} in all three files, bit-identical to an independently
generated reference.

\medskip\noindent
\textbf{Found on the way:} ocp-tool was appending the FESOM grid unconditionally. FESOM writes its
own \code{feom} entry at runtime in domain-decomposition order; ocp-tool's is mesh order, and the
two disagree. Now behind \code{ocean.write\_oasis\_grid}, default off. \emph{This changes default
output for every FESOM config, not only ours.}

\subsection{Declaring the OASIS coupling (2026-08-03)}

Field names on the ice side come from the ism-mapper itself
(\code{cplng\_config\_mod.F90}): \code{<prefix>\_Precip\_liquid}, \code{\_Precip\_solid},
\code{\_Evaporation}, \code{\_Runoff}, \code{\_Soil4T}, \code{\_SST} inbound and
\code{<prefix>\_plit} out. On the OIFS side \code{A\_Evap\_ISM}, \code{A\_SST\_ISM} and
\code{A\_Soil4T\_ISM} are what \code{ecearth.F90} declares for the direct path; precip and runoff
are reused from the ocean path.

Two constraints the parser caught, both of which would have been expensive later:
\begin{itemize}
\item \code{A\_Runoff} is on \code{atmr}, not \code{atma}, so it needs its own exchange line and
      its own direction. Grouping it with precip fails the same-grid validation.
\item \code{include\_models} is consumed before general-level \code{choose\_} blocks resolve, so
      \code{ismm} must sit in the \code{develop-is} \code{add\_include\_models}. It moves together
      with \code{smb\_coupled}: a launched \code{ismm} with no coupled fields deadlocks OASIS.
\end{itemize}

\subsection{Generating the weights (2026-08-03)}
\label{sec:weights}

Weights are not left to OASIS at model runtime. \code{ocp\_tool/oasis\_weights.py} precomputes
them with pyOASIS taken from the coupled model's own OASIS build, ported from rdy2cpl: one MPI
rank per link, each calling \code{enddef()} so SCRIP writes that link's \code{rmp\_*.nc}. Geometry
is read back from the OASIS description files, so the \code{ismp} entry of \S\ref{sec:grid} is
exactly what a link consumes. It needs compute nodes; the one-rank-per-link parallelism is what
makes it tractable.

Tested on 3 nodes against ocp-tool's own TCO95/CORE3 output:

\begin{tabular}{@{}llr@{}}
\toprule
link & map & result \\
\midrule
\code{A096 $\to$ ismp} & \code{BILINEAR D}  & 69\,MB \\
\code{R096 $\to$ ismp} & \code{GAUSWGT D}   & 122\,MB \\
\code{ismp $\to$ A096} & \code{GAUSWGT LR}  & 44\,MB \\

\code{ismp $\to$ A096} & \code{CONSERV}     & OASIS abort, rc=1 \\
\bottomrule
\end{tabular}
\end{center}

\noindent
\textbf{Why the ice$\to$atm conservative and bilinear maps die.} 381 of the 579121 cells have a
corner longitude spread above $180^\circ$ along the polar seam, and the pole cell's four corners
sit at $-135, 135, 45, -45$, encircling the pole outright. That breaks SCRIP's per-cell longitude
line integral (CONSERV) and its enclosing-quadrilateral search (BILINEAR). Neighbour-based maps do
not care. Same geometry as the reason the areas use spherical excess.

\medskip\noindent
\textbf{Consequence.} \code{plit} reaches \code{suorog} as an interpolated value, not the area
fraction \code{ECE\_LANDICE\_THRESH} is written to read. EC-Earth's bilinear would give the same,
so we are no worse than the reference, but the threshold semantics are looser than ideal.

\subsection{Running it: ten legs to a plausible number (2026-08-04)}
\label{sec:running}

Ten test legs, \code{ismtest1} to \code{ismtest10}. The first six were plumbing, the last four were
physics. Plumbing, briefly: the ism-mapper binary was stale because it had been built by hand
rather than through esm\_master and did not declare the namelist flags the generated
\code{namelist.ismm} set; \code{ismp} was missing from the chunk-1 staged grids because chunk 1
stages from \code{pism\_cavity\_ini/oasis/} and not from the fixed-mesh pool, so both pools now
carry it; and \code{LSendToRunoffMapper} gated the \code{ADD\_FLD} call but not
\code{UpdateISMForcing}, which then looked for a field that had never been declared.

\medskip\noindent
\textbf{The mask wipe.} \code{ismtest6} and \code{ismtest7} died the same way, at the clamp in
\code{ece\_updclie\_cpl.F90}. \code{updtim} runs every timestep, the ISM coupling period is
86400\,s and the OIFS timestep is 3600\,s, so 23 steps out of 24 deliver nothing. On those steps
the receive buffer still holds the \code{-HUGE} it was initialised to, and \code{CPLNG2\_EXCHANGE}
does not tell the caller that nothing arrived: it accepts \code{OASIS\_Ok}, which means \emph{call
succeeded, no transfer}, in the same branch as the five statuses that do mean data arrived. An
OASIS restart does not save you. It is read correctly at $t=0$ and overwritten on the next step.

We fixed it on our side with \code{ECE\_LANDICE\_FROM\_OASIS}, default \code{.false.}, so the
OASIS-driven mask update is opt-in and \code{ECE\_LANDICE} keeps reading \code{plit\_oifs} at leg
init. That is a workaround, not a fix. Any other \code{OASIS\_IN} field whose coupling period
exceeds the timestep has the same exposure. Issue drafted for the SMHI tracker.

\medskip\noindent
\textbf{Temperatures ten times too large.} \code{ismtest8} delivered \code{antar\_Soil4T} around
2600\,K. The \code{gauswgt\_avg} method had been copied from \code{gauswgt\_c} and inherited its
\code{CONSERV GLBPOS} postprocessing, which rescales the target field so the global integral
matches the source. Source and target cover different areas, so the ratio is the whole error:
A096 active area $359.41\times10^6$\,km$^2$ over \code{ismp} active area $36.03\times10^6$\,km$^2$
is $9.975$. \code{CONSERV} belongs on a flux you are closing a budget with, between grids that
cover the same domain. Neither holds here. Removed.

\medskip\noindent
\textbf{Too wet and too warm: the source grid was ocean-masked.} \code{ismtest9} ran clean and
produced \code{antar\_smb\_1900.nc} with no sentinels, which is the first end-to-end success. The
numbers were still wrong, and the way they were wrong took a second look to see, because a
first pass mistook the precipitation units. \code{A\_Precip\_liquid} and \code{A\_Precip\_solid}
are divided by \code{RHOH2O} where they are set, so they are m/s. \code{A\_Evap\_ISM} is not, so
it is kg\,m$^{-2}$\,s$^{-1}$. Mixed units in one exchange line.

The comparison that matters is against OIFS's own gridded output from the same leg, over cells
that are actually ice sheet, annual means in mm\,w.e./yr:

\begin{tabular}{@{}lrrrl@{}}
\toprule
 & $P$ & $E$ & $R$ & $T_{\text{soil4}}$ \\
\midrule
OIFS \code{lsp+cp}, \code{e}, \code{ro} over its own ice cells & 212 & 31 & 8.6 & -- \\
\code{ismtest9}, all ISM fields on \code{atma}   & 426 & 28.1 & 11.4 & 256.9\,K \\

\noindent
All three ISM-mapper rows are masked to PISM's own \code{thk}$>$10\,m, 215030 cells,
$13.8\times10^6$\,km$^2$. \code{ismtest9} was 2.6 times too wet and 18\,K too warm. Every ISM
field had been declared on \code{atma}, the ocean-masked A096, where 95\% of the cells south of
$75^\circ$S are excluded; the GAUSWGT stencil then draws from what is left, which is the Southern
Ocean. Ocean precipitation is heavier and the ocean is warmer, and both show up exactly that way.

\code{atmr} (R096) is the same 40320-point reduced Gaussian grid with the land mask instead, it is
already declared in \code{oifs.grids}, \code{A\_Runoff} already uses it, and the
\code{R096 $\to$ ismp} weights already exist. Moving \code{A\_Evap\_ISM} and \code{A\_Soil4T\_ISM}
to it is a one-line config change. \code{A\_Precip\_liquid} and \code{A\_Precip\_solid} are not,
because they are the same fields the ocean coupling uses, and the ocean needs them on \code{atma}.

\medskip\noindent
\textbf{\code{FIELD@grid}.} EC-Earth solves this by naming a different grid per namcouple entry,
which is what OASIS is built for. esm\_tools cannot: \code{coupling\_fields[field]["grid"]} holds
one grid per field, full stop. The obvious workaround is to declare \code{A\_Precip\_*\_ISM}
aliases in OIFS, but that means editing code AWI-ESM3 shares with EC-Earth in order to work around
a weakness in our own runscript engine, which is the wrong direction.

So the syntax gained a per-link override. \code{A\_Precip\_liquid@atmr} in a
\code{coupling\_target\_fields} line uses \code{atmr} for that line and leaves the field
declaration alone. It is 30 lines in \code{coupler.py}: one splitter, applied at each of the three
places that parse a coupling string. Verified against the generated \code{namcouple}, where the
ISM line now reads \code{R096 ismp} and the ocean line still reads \code{A096 feom}.
esm\_tools \code{b0555452f}.

\medskip\noindent
\textbf{\code{ismtest10}: the first SMB we believe.} $P=168$, $E=12.9$, $R=8.4$, so
$\mathrm{SMB}=P-E-R=147$\,mm\,w.e./yr over the PISM ice mask, 99.4\% of the precipitation solid,
mean soil layer 4 at 239\,K. Verified in detail in \S\ref{sec:verify}.

\subsection{Verifying the delivered field (2026-08-04)}
\label{sec:verify}

Three questions. Does the remap preserve the field, is the field itself any good, and where does
it sit against what is known about Antarctic precipitation in this class of model.

\medskip\noindent
\textbf{An orientation trap first.} The PISM file's \code{y} coordinate variable runs opposite to
its own data arrays. Forward-projecting the file's \code{lat}/\code{lon} at a given index lands at
$-y[i]$, not $y[i]$. The file's \code{lat}/\code{lon} are the trustworthy pair: the northernmost
ice cell they identify is at $-62.93^\circ$, $-60.56^\circ$, which is the tip of the Peninsula. Read
straight off the \code{y} axis instead and the same cell comes out at $-119^\circ$, in the Amundsen
Sea, where no ice reaches that latitude. Sampling an OIFS field onto the PISM mask through the
\code{y} axis therefore mirrors Antarctica through the pole, and because the ice sheet is roughly
polar-centred the result still looks plausible. What settles it independently is the lapse rate.
Correlating the delivered \code{antar\_Soil4T} against PISM's own surface elevation gives $-0.896$
and $-10.30$\,K/km as written, against $-0.693$ and $-8.38$\,K/km mirrored. So the \code{ismp}
grid ocp-tool built agrees with PISM's data arrays, and the delivered fields are in the right
place.

\medskip\noindent
\textbf{The remap is faithful to 1\%.} Sampling every OIFS output cell whose centre falls inside
PISM's \code{thk}$>$10\,m mask, 7918 cells, and comparing against the same mask on the PISM side:

\midrule
all ice                      & 166.7 & 168.2 & $+0.9\%$ \\
grounded margin, $<2500$\,m  & 245.3 & 247.1 & $+0.7\%$ \\

\noindent
GAUSWGT is not conservative, so this is agreement rather than a guarantee, but at under 1\% over
the ice sheet the OASIS chain is not where any remaining error lives. $E$ and $R$ are not expected
to match this closely and do not: \code{A\_Evap\_ISM} is tiles 3--9 only, weighted by tile
fraction, while OIFS's \code{e} is the grid-box total including the ocean tiles.

\medskip\noindent
\textbf{The field itself.} Precipitation falls monotonically with elevation across seven 250\,m
bins, 391\,mm\,w.e./yr below 500\,m down to 38 above 3000\,m, which is the right shape for an ice
sheet fed by coastal cyclones. Integrated: 1725\,Gt/yr over the 12.18$\times10^6$\,km$^2$ of
grounded ice and 297\,Gt/yr over the 1.59$\times10^6$\,km$^2$ of shelves, 2022\,Gt/yr in total.
Grounded SMB from RACMO is of order 2100\,Gt/yr, so we are roughly 18\% low, consistent with being
10\% low on continental precipitation.

\medskip\noindent
\textbf{Against the literature.} This is a known and well-documented bias family, so the numbers
have a reference frame. Roussel et al.\ (2020, \emph{The Cryosphere} 14, 2715) evaluated ERA5
against CloudSat: CloudSat gives 186\,mm\,yr$^{-1}$ continentally and ERA5 is about
$+30$\,mm\,yr$^{-1}$ on top, and over the plateau the gap widens to 29 against 65. A 2025 ACP
study found ERA5 and ten CMIP6 models all overestimate the frequency of supercooled-liquid-bearing
clouds and the snowfall from them, with biases so similar across the ensemble that the authors
attribute them to cloud microphysics rather than to the meteorology. Palerme et al.\ (2017) found
the same overestimate across CMIP5.

Where we land:

\bottomrule
\end{tabular}
\end{center}

\noindent
So we are drier than ERA5 everywhere, below CloudSat continentally, and still carry a plateau wet
bias, though a weaker one than ERA5's. The plateau comparison is the least secure part of this
because CloudSat's near-surface blind zone is roughly the lowest kilometre, which is exactly where
plateau clear-sky precipitation lives. The coastal numbers are on firmer ground.

The second mechanism in the literature is resolution, and it is the one that should worry us at
TCO95. Genthon and Krinner made the margin-versus-plateau split the whole point: smoothed
orography gives weaker lifting at the coastal escarpment, so less moisture is wrung out at the
margin and more of it survives inland. Our dipole, low continentally but high on the plateau, is
that signature. For an ice sheet this matters more than the continental mean suggests, because it
moves accumulation off the fast-flowing outlet catchments and onto the dome, where it thickens ice
that takes millennia to respond. A total that looks right can hide a pattern that is not.

\subsection{The snow cap sends the same water to the ocean (2026-08-04)}
\label{sec:calving}

\code{ece\_fesom\_set\_ocean\_fluxes.F90} caps the HTESSEL snowpack at 10\,m water
equivalent and sends everything above the cap to the ocean as \code{A\_Calving}:

\begin{verbatim}
ZEXSNOW = MAX(SUM(PSP_SG(...)) + SUM(PSNSE1(...))*TSTEP - 10000.0, 0.)
PSURF%PSNSE1(...,1) = PSURF%PSNSE1(...,1) - ZEXSNOW/TSTEP
CPLNG2_FLD(CPLNG2_IDX('A_Calving'))%D(...) = (ZEXSNOW/TSTEP)/1000
\end{verbatim}

\noindent
This is the right closure for an atmosphere with no ice sheet underneath it. Snow falls on
Antarctica, the pack would otherwise grow without bound, and returning the excess to the ocean
mimics an ice sheet in balance calving what it accumulates.

The cap is saturated. Annual-mean snow depth over the PISM ice footprint is 9.952\,m with a global
maximum of 10.0004, and 98.7\% of ice cells sit at or above 9.99\,m. A saturated pack cannot store
anything, so the shed rate equals the net input, which is the same $P-E-R$ we now hand to PISM.
That puts \code{A\_Calving} over Antarctica at roughly 2000\,Gt/yr, against 2033\,Gt/yr of
delivered surface mass balance over the same mask.

\medskip\noindent
\textbf{So the water is counted twice} the moment PISM is in the loop. It grows the ice sheet and
it freshens the Southern Ocean, and only one of those can be right. There is no runoff-mapper
diagnostic in the output, so this is inferred from the saturation condition rather than measured.
Adding one is the cheapest way to close it.

The fix is to stop OIFS shedding over the PISM domain and let PISM's own discharge be what reaches
FESOM instead. \textbf{That return path already exists.} \code{pism2esm} calls \code{pism2ocean}
unconditionally, \code{iter\_coup\_interact\_method\_ice2oce} is already
\code{BASALSHELF\_WATER\_ICEBERG\_MODEL}, and
\code{iterative\_coupling\_pism\_ocean\_prepare\_ocean\_icebergmodel\_forcing} writes
\code{latest\_discharge.nc} from PISM's \code{tendency\_of\_ice\_amount\_due\_to\_discharge}. On the
other side, fesom-2.7 already has \code{disch\_file} pointing at exactly that file, behind
\code{use\_landice\_water} and \code{use\_icesheet\_coupling}.

The whole chain is switched off by one flag. \code{iceberg\_coupling: 0} in the runscript becomes
\code{PISM\_TO\_OCEAN=0} and \code{fesom\_use\_iceberg=0}, and \code{pism2ocean} returns in 0.06\,s
with \emph{NOT generating ice forcing for ocean model}. So closing the double count is a
configuration change and a test, not a piece of development.

Note what the selected method deliberately leaves out: the basal-shelf line is commented out, so
only discharge returns, not basal melt. That is right for us. FESOM computes the cavity melt
itself and PISM consumes it through \code{-ocean given}, so sending PISM's basal melt back would
double count in the other direction.

What is genuinely untested is whether it runs. \code{use\_icebergs} is \code{.false.} in every
FESOM namelist we ship, and the helper that would tell the iceberg module how many bergs to seed,
\code{get\_ib\_num\_after\_ice\_sheet\_coupling}, is commented out.

\medskip\noindent
\textbf{This does not taint the moving-cavity results.} Without PISM returning mass, the shedding
was the correct closure and the ocean saw a balanced ice sheet, which is what those runs assumed.

\subsection{PISM eats what OIFS gives (2026-08-05)}
\label{sec:direct}

\code{just\_copy\_stuff.functions} copied \code{atmosphere\_file\_for\_ice.nc} out of another

On the ice side, \code{ablation\_method: DIRECT} builds the surface-given file straight from the

\subsection{The mesh regeneration stopped writing the ocean grid (2026-08-05)}
\label{sec:regenbug}

\code{ismtest11}'s second cycle died on every one of 1792 ranks:

\begin{verbatim}
MCT::m_SparseMatrixPlus:: FATAL--length of vector x different from column count
of sMat. Length of x = 208432   Number of columns in sMat = 208810
\end{verbatim}

208432 is the new mesh, 208810 the old. The chunk-2 namcouple correctly declared the new size while
all three staged \code{rmp\_*feom*.nc} still carried the old one.

The cause was ours, from two days earlier. Gating ocp-tool's FESOM export behind
\code{ocean.write\_oasis\_grid} is right for the initial pool, where FESOM writes \code{feom} itself
at runtime. It is wrong for the regeneration, which needs the grid present precisely so the new
weights can be built against it. \code{permute\_feom\_to\_runtime} then found nothing to permute and
refused to continue, correctly.

\medskip\noindent
\textbf{A second bug, not ours, and worse.} \code{couple\_in} did exit 1. The generated run script
backgrounds it and lets \code{observe\_couple\_in} submit the next leg regardless of its status:

\begin{verbatim}
ice2fesom > log 2>&1 &
process=$!
esm_runscripts ... -t observe_couple_in -p ${process} ...
wait
\end{verbatim}

So a cleanly reported failure still cost a 32-node MCT abort. Left alone, since it is shared
\code{esm\_runscripts} behaviour for every setup. Mitigated instead by a post-condition: after
regeneration the new weights are checked against \code{nod2d.out} and a mismatch is named with both
sizes rather than reaching MCT.

\subsection{Which way the ice sheet's water reaches the ocean (2026-08-05)}
\label{sec:fwreturn}

Two routes exist. The runoff mapper can take the ISM's basal melt and discharge directly, summing
them into runoff and calving. Or the discharge can become icebergs.

The first was built and then thrown away. It worked, and the arithmetic checked out: converting
PISM's gridded \code{kg\,m$^{-2}$\,yr$^{-1}$} to m/s and integrating gave $-11222.3$\,Gt/yr of
discharge against $-11222.3$ in PISM's own \code{ts} file. But it ran PISM's discharge through the
feedback file, the ISM-mapper and a new OASIS link to arrive where the runoff mapper could have
been handed it, and it is not the route we want physically. Icebergs drift and melt over months
across a wide area; a runoff-mapper flux is deposited at the calving front immediately.

\medskip\noindent
\textbf{Kept from that work:} the runoff mapper upgrade. Ours was an ancestor of EC-Earth4's, four
coupling fields and a three-entry namelist. The new one brings \code{IgnoreCalvingBasins}, which is
needed whichever route the water takes: the atmosphere's snow-cap calving over Antarctica has to
stop, or it is counted twice (\S\ref{sec:calving}). Basin 66 is Antarctica exactly, 13383 land cells
from $89.5^\circ$S to $64.2^\circ$S, none north of $60^\circ$S, and 1537 ocean calving points. Our
one local change, dropping the calving enthalpy conversion, was already upstream.

\medskip\noindent
\textbf{The iceberg route, and why not the plugin.} \code{fesom\_icb\_pism} registers
\code{esm\_tools.plugins} entry points, and \code{esm\_plugin\_manager} imports every registered
plugin at startup. Installing it pulled \code{pyfesom2} into every \code{esm\_runscripts} call,
icebergs on or off, and on this machine that stack does not import: \code{libproj} wants a
\code{libstdc++} newer than \code{/lib64} has, and \code{cmocean} calls
\code{matplotlib.cm.register\_cmap}, gone since matplotlib 3.9. An unrelated config check died
because of an iceberg plugin.

So the two halves are split by weight, the way ocp-tool is already handled. The generator needs
\code{pyfesom2} and runs as a subprocess under the ocp-tool python, from \code{couple\_in}, right
after \code{latest\_discharge.nc} is written. Counting the bergs into \code{icebergs\%ib\_num} needs
nothing and is a core prepcompute step with no entry point.

No berg set is seeded. \code{icb\_felem} indexes the mesh, and the mesh changes every chunk, so the
set is rebuilt per leg from that leg's discharge and mesh. Run 1 starts empty, because PISM has not
run yet.

\subsection{Bringing up icebergs: ten defects (2026-08-05)}
\label{sec:icb}

The freshwater route is icebergs, not the runoff mapper's own ISM inputs
(\S\ref{sec:fwreturn}). Getting a leg to start took seven submissions. Five of the six things in
the way were already broken; one was ours. Listed because the pattern says something about how
much of this path had been exercised before.

\begin{enumerate}
\item \textbf{The plugin poisons every run.} \code{fesom\_icb\_pism} registers
      \code{esm\_tools.plugins} entry points, and \code{esm\_plugin\_manager} imports every
      registered plugin at startup. Installing it pulls \code{pyfesom2} into every
      \code{esm\_runscripts} call, icebergs on or off. On this machine that stack does not import:
      \code{libproj} needs \code{GLIBCXX\_3.4.26} and \code{/lib64} stops at 3.4.25, and
      \code{cmocean} calls \code{matplotlib.cm.register\_cmap}, removed in matplotlib 3.9. An
      unrelated config check died because of an iceberg plugin. Proved by \code{LD\_PRELOAD} both
      ways: the old \code{libstdc++} first reproduces it, the conda one first fixes it.
\item \textbf{\code{with\_icb} cannot be set from a \code{choose\_} block.} fesom's
      \code{choose\_with\_icb} resolves first, so the whole iceberg block stays off while every
      flag reads true. It goes in the driver runscript beside \code{with\_recom}.
\item \textbf{\code{bleach 5.0.0}} in the shared spack python has a malformed requirement,
      \code{tinycss2 (>=1.1.0<1.2)}, missing a comma. It breaks \code{pkg\_resources} whenever
      plugins are scanned, which is exactly when \code{with\_icb} is on. Upstream's 5.0.1
      changelog entry is \emph{Add missing comma to tinycss2 require}.
\item \textbf{\code{prepcompute\_recipe} under \code{choose\_with\_icb} is never read.} The live
      recipe is \code{general.prepcompute\_recipe}; the fesom one sits in the finished config
      unused, 17 steps against 19. So \code{prep\_icebergs} and
      \code{apply\_iceberg\_calving\_to\_namelists} have \emph{never run for anyone}, and the
      plugin's only effect to date has been the import of item 1.
\item \textbf{\code{icb\_calving\_day.dat} is missing everywhere.} FESOM opens it
      \code{status='old'} and reads \code{ib\_num} values, in both \code{init\_icebergs} and
      \code{init\_icebergs\_with\_icesheet}. It is in neither \code{icb\_inputs} nor the staging
      lists, and \code{\_icb\_generator} does not write it: that writes longitude, latitude,
      length, height, scaling and felem. Found the format in a working ini directory of
      a270124's, one day-of-year per berg.
\item \textbf{Ours.} A config file staged into \code{work/} takes the basename of its
      \emph{source}, so a template named \code{namelist.runoffmapper.ismm} lands under that name
      and the runoff mapper dies on a missing \code{namelist.runoffmapper}. Fixed with a versioned
      directory rather than a rename, since \code{config\_in\_work} set from
      \code{choose\_version} does not merge either.
\end{enumerate}

\medskip\noindent
\textbf{What we built instead of using the plugin.} The two halves are split by weight, the way
ocp-tool is already handled. \code{make\_icebergs.py} needs \code{pyfesom2} and runs as a
subprocess under the ocp-tool python from \code{couple\_in}, right after
\code{latest\_discharge.nc} is written. \code{count\_icebergs\_into\_namelist} counts them into
\code{icebergs\%ib\_num} and is a core prepcompute step with no entry point, so nothing heavy is
imported unless bergs are actually being made.

That counter cost two of the seven submissions on its own. It has to write to
\code{namelist\_changes} and run \emph{before} \code{modify\_namelists}, which loads, modifies and
writes in one step. Editing the loaded object afterwards, which is what the upstream plugin does,
changes nothing on disk. The first version was right and sat in the dead recipe of item 4, so it
logged the correct \code{ib\_num = 0} while the file on disk kept the template's 1.

\medskip\noindent
\textbf{Four more, found by running it.} The count reached ten.

\begin{enumerate}
\setcounter{enumi}{6}
\item \textbf{\code{icb\_calving\_day.dat} is missing everywhere} (already listed as 5 above).
\item \textbf{Zero bergs kills FESOM.} \code{init\_buoy\_output} defines
      \code{number\_tracer} with extent \code{ib\_num} and then \code{time} as
      \code{NF\_UNLIMITED}. In classic netCDF a zero-size dimension \emph{is} unlimited and only
      one is allowed, so the run dies at step 1 with \code{NC\_UNLIMITED size already in use}.
      \code{ib\_num} is never tested against zero anywhere in the iceberg code; the stepping
      itself is fine with it. Fixed by guarding the five output call sites,
      \href{https://github.com/FESOM/fesom2/pull/962}{FESOM/fesom2\#962}. Verified: before, dies
      at step 1; after, reaches step 3649 and integrates normally.
\item \textbf{The generator needs cell corners nothing writes.} \code{\_get\_coords} reads
      \code{lon\_bnds}/\code{lat\_bnds} to place bergs inside a discharge cell. The PISM griddes
      in the pool carries centres only, so \code{cdo -setgrid} cannot add them and
      \code{latest\_discharge.nc} comes out without: the real pipeline would have failed the same
      way. \code{add\_cell\_bounds.py} supplies them from ocp-tool's own
      \code{PISM.cell\_corners}.
\item \textbf{A guard reads out of bounds on the case it exists to skip.} Nodes of a berg's
      element that a PE does not own are marked 0 seven lines above, and the loop below guards
      against that marker and against nodes with no ocean column in one statement:
      \code{if (iceberg\_node <= 0 .or. ulevels\_nod2d(iceberg\_node) == 0) cycle}. Fortran does
      not promise to evaluate the left side first and ifort does not, so
      \code{ulevels\_nod2d(0)} is read for every halo node, which on a partition boundary is the
      common case rather than a corner one. The control flow was always right, since the
      \code{cycle} is taken either way; the read is not, and in an optimised build it silently
      returns whatever precedes the array. Found by the bounds-checked build of
      \S\ref{sec:icbrestart} within 100 timesteps, fixed as
      \href{https://github.com/FESOM/fesom2/pull/963}{FESOM/fesom2\#963}. Same family as the two
      out-of-bounds reads of \code{\#960}. It is the only instance of the pattern in the iceberg
      sources.
\end{enumerate}

\medskip\noindent
\textbf{The worst one was silent.} \code{count\_icebergs\_into\_namelist} read the couple
directory, which is right from run 2, when the generator writes there. On run 1 the bergs come
from the seed directory instead, so a staged set of 63015 came out as \code{ib\_num = 0} and FESOM
would have ignored every one of them. No crash, no warning, just a run with no icebergs that
looked fine. The zero-berg guard of item 8 is exactly what would have let that pass unnoticed.

\medskip\noindent
\textbf{The generator works.} 63015 bergs from the discharge of the same movcav45 state the PISM
restart comes from (\S\ref{sec:spinup}). All seven files consistent, \code{icb\_felem} inside the
mesh's 405888 elements, latitudes $-76.4$ to $-60.5$ along the Antarctic coast, total mass of
order 2800\,Gt against that state's 4141\,Gt/yr. Banked as the chunk-1 set, valid for that mesh
only. \code{scaling} is 1 throughout, so these are 63015 individual bergs rather than a smaller
set standing in for more; the awiesm-2.1 reference compressed the count with
\code{scaling\_factor [100, 50, 10, 1, 1, 1]}, worth revisiting if advection is slow.

\medskip\noindent
\textbf{How many bergs.} A PISM discharge of 4141\,Gt/yr produces 63015 bergs at
\code{scaling\_factor} 1, and 72\% of them are under 0.1\,km$^2$. Measured against an otherwise
identical leg with \code{ib\_num=0}: 0.0948 against 0.0754\,s per FESOM step, so the uncompressed
set costs $+26\%$, about 33 minutes against 26 for the year.

That is affordable, and the first instinct was to keep the sampling and pay it. The code says
otherwise. \code{icb\_thermo.F90} scales the flux to the ocean by \code{scaling(ib)}:

\begin{verbatim}
hfb_flux_ib(ib) = H_b * length_ib*length_ib*scaling(ib)
dh_b = M_b*dt*REAL(steps_per_ib_step)   !*scaling(ib)
\end{verbatim}

\noindent
but deliberately not the decay. A model berg melts at the rate of a berg of its chunk's
\emph{mean} size, and melt is non-linear in size, so the factors change the answer. They are a
physics parameter, not a cost knob, and an unrun value is an unchecked one. So the awiesm-2.1
values \code{[100, 50, 10, 1, 1, 1]}: 1227 model bergs standing for 65219 real ones, mass
conserved exactly at 2756\,Gt.

The CAV-ICB reference goes further, \code{[250, 100, 30, 2, 1, 1]} for 485 bergs, on a finer mesh
where advection bites harder. The $+26\%$ measurement is recorded here so that sampling more, if it
is ever wanted, is an experiment against a baseline rather than a guess.

\medskip\noindent
\textbf{Finn Heuer's CAV-ICB plugin} solves the neighbouring problem: it derives the calving mass as
a residual of FESOM's own cavity melt minus accumulated Antarctic snow, which is what you need when
there is \emph{no} ice sheet model. With PISM the discharge is known, so its core is not for us.
Three of its downstream details are better than ours and worth taking: calving days with an austral
summer intensification for the small classes rather than a flat spread,
\code{exclude\_occupied\_elements}, and a considered \code{ibareamax} of 100 against the inherited
default of 400.

\medskip\noindent
\textbf{Since verified.} Chunk 2 generated its bergs in run and exercised the \code{feom} fix of
\S\ref{sec:regenbug} at the same time, both on the first attempt (\S\ref{sec:chunk2}).

\subsection{The corrupted iceberg restart: an off-by-one in a calving day (2026-08-05$\to$06)}
\label{sec:icbrestart}

Chunk 1 ran its full year with 1227 bergs and then wrote a restart FESOM cannot read back. One
row of 1227 had 25 fields instead of 26, with field 18 reading \code{0.0000000E+0010995116}.
The \code{'(18e15.7,I8,L,3e15.7,L,I5,L)'} format puts no separator between fields, so an
\code{iceberg\_elem} that fills all eight digits of the \code{I8} butts against the preceding
\code{e15.7} and the record stops parsing. The corrupt row was always the last one, and the other
1226 carried valid elements between 1385 and 404434 on a 405888-element mesh.

The obvious suspect was the local-to-global conversion, \code{iceberg\_elem =
partit\%myList\_elem2D(iceberg\_elem)}, which has no range check on either side. FESOM was rebuilt
with \code{-check bounds -check pointers -traceback -g -O0} on the seven iceberg sources to trap
it.

That build did not trap the corruption, but it did trap something else within 100 timesteps,
which is item 10 below and is now
\href{https://github.com/FESOM/fesom2/pull/963}{FESOM/fesom2\#963}. With that fixed the year ran
clean to the restart write, and the restart reproduced the defect exactly: 1227 rows, one
malformed, row 1227.

\medskip\noindent
\textbf{It was ours, and bounds checking could never have found it.} The generator writes
\code{icb\_calving\_day.dat} by spreading the set across the year as
$1 + 364\,i/(n-1)$, which gives the last berg exactly \code{365.0000}. FESOM calves on

\begin{verbatim}
if( real(istep) > real(step_per_day)*calving_day(ib) ) then !iceberg calved
\end{verbatim}

\noindent
so that berg needs step 26281 in a year of $72 \times 365 = 26280$. It never calves,
\code{iceberg\_step1} never runs for it, and \code{iceberg\_elem(ib)} is only ever assigned inside
that routine. The array is allocated and never initialised, which is visible on the very next line
of \code{icb\_allocate.F90}:

\begin{verbatim}
allocate(iceberg_elem(ib_num))
allocate(find_iceberg_elem(ib_num))
find_iceberg_elem = .true.
\end{verbatim}

\noindent
so \code{iceberg\_out} writes whatever was in that memory. Nothing ever indexes with the value, so
there is no out-of-bounds access for \code{-check bounds} to see. The decisive evidence is field 19
of the bad row: \code{find\_iceberg\_elem} is still \code{T}, where every calved berg has it
\code{.false.} after its element search, and the velocities are zero for the same reason. The value
10995116 is byte-identical across two runs, so it is deterministic uninitialised memory rather than
anything random.

Fixed by ending the spread at day 364 (\code{a6e0f496}). The existing restarts were repaired in
place by dropping the single bad row, which costs one berg of \code{scaling} 1 that never entered
the ocean and delivered no freshwater. 1226 rows, all well formed, all elements inside the mesh.

The FESOM half is worth a patch on its own and is not yet sent: an uninitialised array should not
reach a restart file, and any berg whose calving day falls past the end of a leg hits this,
not only ours.

\subsection{Chunk 2: what the second leg cost (2026-08-06)}
\label{sec:chunk2}

Chunk 2 is the first leg that generates bergs in run and the first that exercises the \code{feom}
fix of \S\ref{sec:regenbug}. Both worked on the first attempt. The coupling produced 842 bergs from
PISM's discharge with 1226 carried over, added \code{lon\_bnds} inside the pipeline, regenerated the
mesh to 208094 nodes, validated the weights against it and remapped the OASIS restarts. Two
further defects then stopped the leg, both of the same family: a per-leg file wired to a path that
nothing maintains.

\medskip\noindent
\textbf{The iceberg inputs were frozen at run 1.} \code{reuse\_sources} redirects every reusable
filetype to the experiment input pool from run 2 onwards. The bergs are \code{input} files, so
FESOM was given run 1's 1227-line set while \code{ib\_num} had been counted from the new one at
$1226 + 842 = 2068$, and the read loop

\begin{verbatim}
do i = 1+num_non_melted_icb, ib_num
   read(97,*) lon_deg(i)
\end{verbatim}

\noindent
ran off the end of the file. Fixed by giving fesom its own \code{reusable\_filetypes} without
\code{input} (\code{b91ae5af}); that pool holds the iceberg files and nothing else, so the
optimisation was buying nothing here. With it in place the staging delivers 842, 1226 and 2068 and
FESOM logs \code{read iceberg restart file} and initialises on all of it.

\medskip\noindent
\textbf{The ISM-mapper's forcing file was truncated by our own script.} It aborts at startup with

\begin{verbatim}
2273: *EE*OASISNetCDF: Invalid dimension ID or name
2273: Aborting ISM-Mapper.
\end{verbatim}

\noindent
Despite the prefix that is not OASIS. \code{oasis\_enddef} completes cleanly in
\code{debug.root.06}; the string is netCDF's \code{NC\_EBADDIM} passed through the mapper's own
wrapper, \code{call ERROR("OASIS"//nf90\_strerror(iret))}, and it is raised by
\code{nf90\_inq\_dimid(forcing\_file\_id, "time"/"y"/"x")}.

That forcing file is \code{antar\_pism2ece.nc}, and it has two consumers on two grids. OIFS's
\code{suorog} reads \code{plit\_oifs(ny{=}1, nx{=}40320)} in gridpoint order, and the ISM-mapper
reads \code{plit(time, y, x)} on PISM's $761 \times 761$ grid. Our \code{make\_plit\_oifs.py}
opened it \code{nc.Dataset(out, "w")}, which truncates: it wrote its own half and destroyed the
mapper's.

\begin{verbatim}
chunk 1:  ny, nx, time=14, y=761, x=761    plit_oifs + plit
chunk 2:  ny, nx                            plit_oifs only
\end{verbatim}

\noindent
Chunk 1 never sees it because \code{couple\_in} is skipped there and the pre-staged file keeps both
halves. Chunk 2 is the first leg that runs the script, so it is the first leg that breaks the file.
Fixed by appending rather than truncating, with a size check on \code{nx}
(\code{18c712b2}). The damaged file was rebuilt from PISM's chunk-1 end state, which is a better
\code{plit} than the initial geometry it had carried before: 37.0\% ice cells.

\medskip\noindent
\textbf{And a stale \code{rstism.nc}, which was real but was not this.} The chunk-2 rule pointed it
at \code{oasis\_regen/}, where nothing writes an \code{rstism}, so it served a 4.6\,MB seed holding
only \code{antar\_plit} against the 8.5\,MB file chunk 1 had written with all seven fields and
their \code{LOCTRANS} accumulators. Fixed by carrying it forward from the previous leg like any
other OASIS restart; no remapping is involved, since none of the \code{ismm} links touch
\code{feom}. Staging the correct file did not stop the abort, which is what pointed at the forcing
file instead (\S\ref{sec:falsified}).

\medskip\noindent
\textbf{On reading logs from the wrong end.} That one line sits 17000 lines above 362 copies of
\code{Transport retry count exceeded} on the InfiniBand link, and the transport errors are simply
the other ranks timing out against a dead peer. All 362 are OIFS ranks and none are FESOM, which
fits, and they all name the same remote queue pair. Three submissions and a node exclusion went
into the fabric reading before the head of the log was read (\S\ref{sec:falsified}). The tell was
available from the start: two of those failures drew the same allocation, but the third drew
\code{l[10700-10731]} and died identically.

\subsection{Getting chunk 2 to run, and two things I had wrong (2026-08-07)}
\label{sec:chunk2run}

Chunk 2 ran. \code{ib\_num = 1883}, 948 bergs carried and 935 calved, on a mesh regenerated to
208094 nodes, with no ISM-mapper abort and no OIFS overflow. It took a clean experiment to get
there, because \code{ismtest25} had accumulated too many hand repairs to be evidence of anything:
a repaired restart, hand-filtered berg files, a manually rebuilt \code{plit}, eighteen resumes.

\medskip\noindent
\textbf{The ISM-mapper abort was a field nobody writes.} \S\ref{sec:chunk2} blamed
\code{make\_plit\_oifs.py} truncating \code{antar\_pism2ece.nc}, and that was real but only half
of it. On the clean run the script logged \code{mode=w, kept []}: the file did not exist at all, so
appending had nothing to append to. The PISM-grid \code{plit(time,y,x)} the mapper reads is written
by \code{make\_pism2ece\_plit.py}, which is a hand-run prep script with \emph{no call site
anywhere}. Chunk 1 survives only because it stages a pool copy that someone once prepared by hand
and which happens to carry both halves; chunk 2 builds the file fresh and gets the OIFS half alone.
Now built in \code{couple\_in} from the leg's own \code{latest\_ice\_geometry.nc}
(\code{c420e243}). That file carries PISM's ice-type mask rather than thickness, so the script
takes \code{mask} $\in \{2,3\}$, grounded and floating, which agrees with \code{thk > 1}\,m to
within 40 cells of 214082 on the same state. It refreshes rather than skips, so the mask follows
the moving ice sheet instead of freezing at the initial geometry.

\medskip\noindent
\textbf{The OIFS overflow did not recur on this leg.} Chunk 2 had died repeatedly with
\code{forrtl: error (72): floating overflow} at \code{callpar.F90:680}, which is
\code{EXP(PSD\_VD(JL,YLZ0H))}, the exponential of the log roughness length for heat. With the
mapper alive this leg ran through without it, and at the time that read as the overflow being the
atmosphere falling over after a dead peer, the same way the transport errors of
\S\ref{sec:chunk2} were. It came back on 2026-08-10 with the mapper running and no dead peer
(\S\ref{sec:lz0h}), so the absence here was the intermittency, not a cure.

\medskip\noindent
\textbf{PR \href{https://github.com/FESOM/fesom2/pull/964}{FESOM/fesom2\#964}} was merged before
this leg and carries two things we need. \code{cap\_ibhf\_n} bounds iceberg-driven cooling at
$-1.85$\,\textdegree C per cell per step, and it binds: 447 firings in the first 1600 steps, 207
cells and $1.17\times10^{12}$\,J discarded in one of them. Whether that rate is the safety net
working or a statement about our iceberg heat flux is an open question, not a settled one. It also
replaces the \code{par\_ex}-then-\code{stop} on an out-of-range \code{iceberg\_elem}, which hung all
1792 ranks, with marking the berg melted. That retires a defect we were going to report.

\medskip\noindent
\textbf{The calving-day fix, verified where it counts.} The clean run's chunk-1 restart is 1227
rows with \emph{zero} malformed, against exactly one before (\S\ref{sec:icbrestart}), and every
\code{iceberg\_elem} inside 1218..404422.

\subsection{The concurrent chain, and two failures that left nothing on disk (2026-08-10)}
\label{sec:concurrent}

The point of \code{coupling\_mode: concurrent} is that the AWI year and the PISM decade run at the
same time and hand over through \code{<model>\_chunk\_<N>.done} markers, instead of the decade
serialising behind the ocean year. It works, and it took two failures to get there, both of which
ended with nothing in the queue and no error anywhere a person would look.

\medskip\noindent
\textbf{Chunk 1 has no AWI year to consume, so it boots from the pool.} The harvested set the
resolver picked was from 24 July, and its \code{atmosphere\_file\_for\_ice.nc} is a 48\,MB field on
a 192$\times$96 Gaussian grid, from a pipeline where the atmosphere forcing had not yet moved onto
the ice grid. Ours is 334\,MB on PISM's 761$\times$761. With \code{regrid\_method: NONE} the guard
in \code{coupling\_atmosphere2pism.functions} compared 192 against \code{ice.griddes}' 761 and
stopped, which is correct. PISM then died in 43 seconds with no output, and the log said
\code{PISM ERROR: No such file or directory} about \code{latest\_atmo\_forcing\_file.nc}, because
the guard exited without writing the sentinel \code{observe.py} reads, so the chain started PISM
anyway and the message naming the grid never surfaced.

The pool went stale because the harvest was never switched on: \code{ismtest} runscripts set
neither \code{harvest\_parallel\_ini} nor \code{pism\_grid\_tag}, so \code{COUPLING\_IDENTITY} came
out empty and \code{harvest\_pism\_bootstrap} returned early on every serial leg that could have
refreshed it. Both keys are set now, the July set is retired in place, and the pool carries a set
taken from \code{ismtest26}'s own \code{couple/} directory, verified at \code{xsize} 761 against
\code{ice.griddes} before publishing. The guard writes the sentinel (\code{afa683d5}).

\medskip\noindent
\textbf{Then the chains deadlocked, and the design says they cannot.} PISM ran its decade, wrote a
restart, and its \code{couple\_out} died at \code{add\_cell\_bounds} before reaching
\code{touch\_coupling\_marker}. No \code{pism\_chunk\_1.done}, no sentinel either, so the AWI chain
parked on a marker that would never arrive and PISM exited clean into its second decade.
\code{concurrent\_coupling.py} argues mutual parking is impossible because ``markers are monotone
per chain, and a chain only parks on a marker the sibling has not yet produced, which implies the
sibling is still running''. That holds only if a leg either writes its marker or crashes loudly.
This one did neither.

The cause is a name collision. \code{coupling\_pism2esm.functions} sourced
\code{coupling\_pism2ocean.functions} and then
\code{../fesom/coupling\_ice2fesom\_interactive\_mesh.functions}, and both define
\code{iterative\_coupling\_pism\_ocean\_prepare\_ocean\_icebergmodel\_forcing}. The later
definition wins, so the dispatch in \code{coupling\_pism2ocean.functions} reached the AWI berg
pipeline rather than this chain's own two-line discharge step. That pipeline wants
\code{ICB\_BASIN\_FILE} and \code{OCP\_TOOL\_DIR}, which \code{env\_fesom.py} supplies on the other
chain, so \code{add\_cell\_bounds} was called with one argument instead of two and printed its
usage.

In serial the same failure is harmless and had been happening unnoticed in both of
\code{ismtest26}'s PISM legs, because the AWI chain's \code{couple\_in} does the real berg
generation and that part works: \code{all 875 placeable} and \code{all 935 placeable}. In
concurrent mode the identical \code{exit 1} lands in front of the handshake.

Nothing in the PISM \code{couple\_out} chain needs that file. Checking all thirteen functions it
defines against the three files in the chain, the only matches were the colliding name and a
comment reading \code{\# ice2fesom (other file)}. The source line is gone (\code{14797ecb}). The
whole coupling tree has exactly three cross-model sources, and this was the one that closed a
cycle: \code{pism2esm} $\to$ \code{fesom/ice2fesom} $\to$ \code{pism/ocean2pism}.

\medskip\noindent
\textbf{With that removed the cycle closes by itself.} \code{pism\_chunk\_1.done} at 16:12, PISM
parked, \code{awiesm3\_chunk\_1.done} at 16:17, \code{reviving parked chain pism} in the same
second, and PISM went on to finish a second decade and write \code{pism\_chunk\_2.done} unattended.
The decade takes about 16 minutes and now runs inside the ocean year rather than after it.

\medskip\noindent
\textbf{The launcher is under-resourced.} The chain doctor submits its own job per chain with
\code{--nodes=1} hardcoded and a 30 minute default. A mesh-change \code{couple\_in} took 19:15
there, and 29:31 in the serial arrangement where the same work rides inside PISM's four nodes. Ten
minutes of headroom on a step that has already run for twenty-nine, and the failure mode is a leg
dying just before it finishes. \code{coupling\_launcher\_nodes} now exists, defaulting to 4, and
the walltime default is 1:30. All eight bare \code{exit 1} paths in \code{ice2fesom} were converted
to \code{couple\_fail} in the same commit (\code{9edaee35}), so a coupling failure there leaves the
sentinel rather than a parked sibling.

\subsection{The OIFS overflow is not a corpse (2026-08-10)}
\label{sec:lz0h}

The chunk-2 AWI leg died 90 seconds in with \code{forrtl: error (72): floating overflow} at
\code{callpar.F90:680}, with the ISM-mapper alive and no dead peer. \S\ref{sec:chunk2run} said this
crash was the atmosphere falling over behind a dead mapper; that is wrong and is struck in
\S\ref{sec:falsified}.

\medskip\noindent
\textbf{It is a corrupt value, not a drifted one.} \code{LZ0H} is the log of the roughness length
for heat, physically about $10^{-4}$\,m over ocean and $10^{-3}$\,m over snow, so the field lives
between roughly $-10$ and 0. The physics is the single-precision build, where \code{EXP} overflows
above 88.7, meaning $z_{0h} > 10^{38}$\,m. Ninety orders of magnitude separate the physical range
from the crash threshold, which is not a distance bad surface fluxes cover.

\medskip\noindent
\textbf{Two suspects killed by measurement.} The regenerated ICMGG is not the source: \code{lsrh}
(paramId 234, \code{NGRBLSRH}) is identically 0.000 in both the pristine
\code{ICMGGab45INIT\_CORE3} and the ocp-tool regenerated \code{ICMGGab45INIT\_feomdyn}, globally
and inside the cap. Nor is the first step: \code{callpar.F90:552} guards the
\code{VD(LZ0H) = VF(LZ0H)} assignment with \code{NSTEP == NSTART}, so every leg including a warm
start begins from that zero, and the crash arrives 90 seconds later.

The \code{libwam.SP.so} frame directly above \code{callpar} in the traceback is not the wave model.
\code{libwam.SP.so} exports its own \code{expf} and \code{\_\_libm\_expf}, and \code{libarpifs}
links against it, so the \code{EXP} call resolves there.

\medskip\noindent
\textbf{What did change between the legs.} 64 cells altered character in the Antarctic cap, 36 from
land to sea and 28 from sea to land, spanning $-83$ to $-62$ latitude. The \code{updtim} LANDICE
hook does not touch them: despite its own header comment it does not flip the land-sea mask, it
seeds SST and skin temperature and leaves the cells as ocean, and on this leg it reseeded 0 cells
on every rank. Both crashing ranks were among the 20 of 384 that own \code{plit}-active cells,
which locates the failure but says only that those ranks hold land-ice columns.

\medskip\noindent
\textbf{A print, and a staging trap.} \code{callpar.F90:680} now reports the value before the
\code{EXP} whenever $|\code{LZ0H}| > 20$, together with the neighbouring \code{SD\_VF} slots.
\code{LZ0H} is the element immediately after the sub-grid orography and land-sea block in the
packed surface array, so a recognisable fill value, an arbitrary bit pattern and a merely large
computed number each point somewhere different. Rebuilding was not enough: \code{esm\_runscripts}
does not re-stage libraries from run 2 on, and all four copies under the experiment were still the
4 August build with zero occurrences of the marker. The library had to be pushed into the
experiment's own \code{bin/} pool.

\medskip\noindent
\textbf{It did not reproduce.} The rerun of the same leg ran the full year and wrote
\code{awiesm3\_chunk\_2.done}, where the first attempt was dead at 90 seconds, and the print never
fired. The overflow is intermittent, and chunk 2 is closed on the AWI side. The diagnostic lives in
the experiment's \code{bin/} pool, so every later leg carries it and the next firing costs no round
trip.

\subsection{Open}

\begin{itemize}
\item \textbf{Plateau wet bias, margin dry bias.} $+72\%$ against CloudSat above 2500\,m while
      10\% low continentally (\S\ref{sec:verify}). Expected at TCO95 and shared with ERA5, but it
      redistributes accumulation from the outlet catchments to the dome, which is the pattern PISM
      is most sensitive to. Nothing to fix today; something to state whenever a run is interpreted.
\item \textbf{The \code{EXP(LZ0H)} overflow is live and intermittent} (\S\ref{sec:lz0h}). It
      killed a chunk-2 leg 90 seconds in with the ISM-mapper alive, and did not recur on the rerun
      of the same leg. The value has to be corrupt rather than drifted, ninety orders of magnitude
      past physical. The regenerated ICMGG and the first step are ruled out by measurement. A print
      at \code{callpar.F90:680} is in the experiment's \code{bin/} pool and will catch the next
      firing with the neighbouring \code{SD\_VF} slots.
\item \textbf{The concurrent launcher was under-resourced}, one hardcoded node and 30 minutes
      against a \code{couple\_in} that runs 20 to 30. Fixed with
      \code{coupling\_launcher\_nodes}, but no concurrent leg has yet exercised the new default.
\item \textbf{The Southern Ocean freshwater budget is unchecked.} Basin 66 calving is switched off
      in the runoff mapper and the bergs are meant to replace it. Nobody has yet compared what
      leaves the ice sheet against what enters the ocean.
\item \textbf{\code{iceberg\_elem} is uninitialised in FESOM} (\S\ref{sec:icbrestart}). Our
      calving days no longer trigger it, but any berg whose calving day falls past the end of a leg
      still writes uninitialised memory into the restart. Worth a patch alongside \code{\#962} and
      \code{\#963}.
\item \textbf{A failed \code{couple\_in} still cannot stop the chain by its exit code}
      (\S\ref{sec:regenbug}); that is shared \code{esm\_runscripts} behaviour and is left alone.
      Every failure path we own now writes the sentinel instead, which is what \code{observe.py}
      acts on.
\item \textbf{HTESSEL glacier-tile refreezing} is unchecked. It decides whether the shelf-margin
      SMB is meaningful before PISM ever sees it.
\item \textbf{\code{A\_Calving} double-count, about 2000\,Gt/yr} (\S\ref{sec:calving}). Confirmed:
      the snowpack is saturated at the 10\,m w.e.\ cap over 98.7\% of the ice sheet, so everything
      that accumulates is shed to the ocean, and the same water now also grows PISM. Must land
      together with the freshwater return, never before it.
\item \textbf{\code{orog} for the downscaling reference.} \code{field\_def.xml:176} has a \code{z}
      but it is in the \code{3D\_ml} group, so model-level geopotential. Source it from the ICMGG
      with eccodes for param 129, as \code{make\_plit\_oifs.py} does for \code{lsm}.
\item \textbf{\code{usurf\_oifs} writer}, replacing the ICMGG-derived \code{plit} with PISM's own
      mask, and turning \code{ECE\_ISM\_OROG} on.
\item \textbf{\code{PLIT\_antar} is received on \code{atma}}, because \code{ismp $\to$ R096}
      weights were never generated. Harmless while \code{ECE\_LANDICE\_FROM\_OASIS} is off, wrong
      the moment it is turned on for the orography half.
\item \textbf{Freshwater return, partially.} Discharge now reaches FESOM as icebergs
      (\S\ref{sec:icb}). PISM basal melt still does not, and that is the remaining leg of the mass
      budget.
\item \textbf{Field set is welded to scheme in ismm.} The direct path supplies 6 fields, dEBM needs
      7 and shares only 2 of them. Splitting the two would unblock dEBM for Greenland and for warm
      scenarios where a positive-degree-day treatment stops being adequate.
\item \textbf{atlas 0.31.1 $\to$ 0.39.0} came in with the vendor merge and is unbuilt.
\end{itemize}

\subsection{Falsified claims (kept, struck through)}
\label{sec:falsified}

\begin{itemize}
\item \dead{Adding a PISM grid means teaching the per-leg regeneration to emit SCRIP weights to
      and from TCO95 on every cycle. This is the expensive part and the main schedule risk.}
      Overstated: the weight machinery is general, so PISM costs a few \code{Link} entries.
\item \dead{OASIS computes the weights itself at runtime, and the PISM grid does not move, so
      there is no per-cycle work.} Wrong twice. Weights are precomputed via pyOASIS
      (\S\ref{sec:weights}), and the links do regenerate per mesh-change leg because the OIFS mask
      moves where PISM is.
\item \dead{CONSERV is the right map for plit, since ECE\_LANDICE\_THRESH reads an area fraction.}
      It aborts on a pole-centred grid (\S\ref{sec:weights}). GAUSWGT is what works.
\item \dead{The ice$\to$atm link is \code{BILINEAR D}.} The SCRIPR letter is the \emph{source}
      grid type and \code{ismp} is logically rectangular, so \code{LR}; and \code{BILINEAR} fails
      here regardless.
\item \dead{Chunk 2's iceberg freshwater flux is 20 to 50 times too high: chunk 1 ends the year at
      1208 and chunk 2 opens at 25641 with the same bergs, so they must be misplaced, and the
      element-area spread amplifies what a misplaced berg delivers.} The premise was a misread.
      Chunk 1 does not end at 1208, it ends at 56093 with a peak of 57367; 1208 is a value from its
      first days, taken from a progress line early in the run and then used as the end-of-year
      baseline in every comparison after. Against the real figure, chunk 2 opening at 25641 with
      $\sim$1200 bergs already afloat is unremarkable. Hours went into re-seating carried bergs and
      arguing about element areas to explain a number that needed no explaining. The re-seat and
      the submesh placement are still right, since stale indices and bergs on land are wrong on
      their own terms, but they were not fixing this.
\item \dead{The OIFS floating overflow at \code{callpar.F90:680}, \code{EXP(LZ0H)}, is a bad
      roughness length in the regenerated ICMGG at a newly-ocean cell.} Tested on 2026-08-10 and
      wrong: \code{lsrh} is identically 0.000 in both the pristine and the regenerated ICMGG
      (\S\ref{sec:lz0h}).
\item \dead{The overflow is the atmosphere dying after a dead peer, and does not happen once the
      ISM-mapper starts.} Held for one leg and then failed. It recurred on 2026-08-10 with the
      mapper alive and nothing else dead, and did not recur on the rerun of the same leg
      (\S\ref{sec:lz0h}). Two clean legs were read as a cure for something intermittent.
\item \dead{\code{couple\_in} should run as its own batch job so it is not at the mercy of the
      login node.} It already ran on compute whenever the workflow drove it, inside PISM's 4-node
      allocation (job 26718445, 4 nodes, COMPLETED in 28:59), and that is where
      \code{regenerate\_oasis\_weights}' inner \code{srun -n 1 --cpus-per-task=64} finds a step to
      land on. Giving it a single-node job of its own deadlocked it against itself,
      \code{step creation temporarily disabled (Requested nodes are busy)}. The login-node failure
      that prompted the change was an editor session holding 1999 of the 2048 RLIMIT\_NPROC
      threads, not a flaw in the design.
\item \dead{The chunk-2 crash is an InfiniBand fault. Two allocations died at step 1 with
      \code{Transport retry count exceeded}, so the nodes are bad and excluding them is the fix.}
      Wrong. The third submission drew a different node set entirely,
      \code{l[10700-10731]}, and died identically. The 362 transport errors are the other ranks
      timing out against a peer that had already aborted 17000 log lines earlier, and the real
      fault is one quiet line, \code{*EE*OASISNetCDF: Invalid dimension ID or name} from the
      ISM-mapper (\S\ref{sec:chunk2}). Cost three submissions and a node exclusion, all from
      reading the tail of the log rather than the head.
\item \dead{The ISM-mapper aborts because chunk 2 staged a stale \code{rstism.nc} holding only
      \code{antar\_plit}, so OASIS fails on the first LAGged link whose source field is absent.}
      The stale file was real and is fixed, but it is not the cause: with the correct 8.5\,MB
      restart staged the mapper aborted identically. The message is not OASIS's at all
      (\S\ref{sec:chunk2}).
\item \dead{The corrupt \code{iceberg\_elem} is written by the local-to-global conversion
      \code{myList\_elem2D(iceberg\_elem)}, which has no range check, or by the invalid
      \code{MPI\_IN\_PLACE} mixing in \code{com\_integer}.} Neither. The value is never written at
      all: the last berg never calves, so \code{iceberg\_step1} never runs for it and the
      uninitialised array reaches the restart (\S\ref{sec:icbrestart}). Both suspects are real
      defects and neither causes this. A bounds-checked build cleared them by not trapping.
\item \dead{\code{plit-active=0} in the log is the symptom of the mask being wiped.} That line
      appears 363 times a leg in \code{eval5}, which runs fine. It is a normal diagnostic and says
      nothing about the crash. The evidence for the wipe is the clamp itself and the delivery
      arithmetic, not this line.
\item \dead{All ISM source fields belong on \code{atma}.} \code{atma} is ocean-masked. Everything
      except SST belongs on \code{atmr} (\S\ref{sec:running}).
\item \dead{The delivered $P$ is 168 against OIFS's own 212, so the remap may be losing
      precipitation.} The 212 came from a snow-depth proxy mask on the remapped output, which is
      coastal-biased. On an identical footprint the two agree to 0.9\% (\S\ref{sec:verify}).
\item \dead{OIFS sits at ERA5's continental Antarctic precipitation of about 216\,mm/yr.} Same
      proxy-mask error. It is 167, which is 10\% \emph{below} CloudSat.
\end{itemize}

\subsection{Method notes}

\begin{itemize}
\item \code{esm\_runscripts -c} assembles the full runtime config and catches grid-consistency and
      component-loading errors. Both config bugs above were found this way, not by reading.
\item \code{esm\_master --check <target>} renders the build without executing it. It also revealed
      the pre-existing \code{debm} section-header failure.
\item Weight generation must run from a shared filesystem. A first attempt with the working
      directory on \code{/tmp} died in 14\,s: \code{/tmp} is node-local on Levante, so the compute
      node could not write the job output.
\item \textbf{A \code{choose\_} block cannot override what another \code{choose\_} block sets.}
      This cost three separate rounds: \code{with\_icb} set from
      \code{choose\_general.ism\_freshwater\_return} left the whole iceberg block off while every
      flag read true; \code{required\_plugins} and \code{prepcompute\_recipe} set from the setup
      lost to fesom's \code{choose\_with\_icb}; \code{config\_in\_work} set from
      \code{choose\_version} never merged. Each time the fix was to move the value to where it
      resolves first, not to try to outrank it. Literals in the driver runscript win, and a
      versioned directory beats renaming a file.
\item The name a config file gets in \code{work/} is the \emph{basename of its source}, not the key
      it is filed under. A template named \code{namelist.runoffmapper.ismm} is staged under that
      name and the model dies on a missing \code{namelist.runoffmapper}.
\item Grid winding is invisible to an area check, which takes an absolute value. Test it
      separately by dotting the corner-polygon normal with the outward radial vector.
\item Do not guess the units of an OASIS field. Read the line that sets it.
      \code{A\_Precip\_*} are divided by \code{RHOH2O} and are m/s, \code{A\_Evap\_ISM} is not and
      is kg\,m$^{-2}$\,s$^{-1}$, and they travel in the same exchange line. Guessing wrong turned
      a factor of 2.6 into an apparent factor of 350 and pointed at the wrong bug.
\item Compare a remapped field against the source model's own output over the \emph{same} mask,
      not over a latitude band and not over a proxy for the mask. Both shortcuts produced a wrong
      answer here, in opposite directions.
\item A polar grid can be mirrored through the pole and still look right, because the ice sheet is
      roughly polar-centred and latitude is unchanged by the mirror. Longitude is not, so check a
      known asymmetric landmark. The Peninsula tip at $-62.9^\circ$, $-60.6^\circ$ settled it here.
      An independent physical check is better still: temperature against elevation gave $-10.3$
      versus $-8.4$\,K/km for the two orientations.
\end{itemize}
