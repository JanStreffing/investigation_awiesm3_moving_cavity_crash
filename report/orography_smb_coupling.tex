\begin{abstract}
\noindent
\textbf{Mission.} Close the atmosphere half of the AWI-ESM3 $\leftrightarrow$ PISM cycle in both
directions: PISM's surface mass balance driven by the OIFS leg that just ran, and the ice-sheet
surface elevation OIFS runs with following the ice sheet PISM produced. The ocean half was closed
by the moving-cavity campaign; this is its companion.

\medskip\noindent
\textbf{Where we are.} The ISM-mapper builds and links as an esm\_tools component, the PISM grid
and all three coupling links are generated and verified, and the OASIS exchange is declared, but
nothing has yet run coupled.

\medskip\noindent
Timeline in \S\ref{sec:campaign}, current state and open items in \S\ref{sec:state}, dead claims
in \S\ref{sec:falsified}.
\end{abstract}

\section{The campaign, in the order it happened}
\label{sec:campaign}

\subsection{Taking stock: the atmosphere side is a stub (2026-08-03)}
\label{sec:taint}

\code{couplings/oifs/just\_copy\_stuff.functions} copies \code{atmosphere\_file\_for\_ice.nc}
verbatim out of \code{a270122/lars\_and\_paul/experiments/E130ka\_coupled3}. Confirmed in
\code{eval5}: a $192\times96$ ECHAM Gaussian grid carrying \code{temp2}, \code{tsurf},
\code{aprt}, \code{orog}, \code{swd}, \code{cc}, \code{q2m}, \code{tau}, \code{emiss},
\code{uv}, \code{TOAswd}.

\textcolor{red}{\textbf{TAINTED}}: every PISM leg of the moving-cavity campaign, \code{eval5} and
\code{fgdbg02} included, ran dEBM on a 130\,ka paleo ECHAM atmosphere. No PISM surface mass
balance number from that campaign is a statement about AWI-ESM3. Ocean-side results are not
affected; they are forced from FESOM output directly.

Two further findings from the same read. \code{suorog.F90:151--250} already implements both
returns: \code{ECE\_CPL\_ISMM} reads \code{usurf\_oifs} and patches \code{ZZOROG} through
\code{REESPE}/\code{SPEREE}, \code{ECE\_LANDICE} reads \code{plit\_oifs}. That code is upstream
(vendor \code{a2e46d5}, Jorge Bernales) and our \code{suorog.F90} is byte-identical to it. But we
run \code{ECE\_LANDICE} only, and the \code{plit} we write is not PISM's ice mask:
\code{make\_plit\_oifs.py} derives it from the regenerated ICMGG land--sea mask capped at
$60^\circ$S. \code{eval5/couple/antar\_pism2ece.nc} holds one variable, \code{plit\_oifs},
\code{nx}=40320. No \code{usurf\_oifs}. So no PISM geometry reaches the atmosphere at all.

\subsection{Choosing the ISM-mapper over XIOS (2026-08-03)}

Everything dEBM needs is already in the XIOS output, and the de-accumulation pattern exists in
\code{field\_def\_lpjg\_safe.xml.j2}. Checked against \code{eval5} year 1903: \code{ssrd}
$=6.845\times10^5$ and \code{tisr} $=1.226\times10^6$\,J\,m$^{-2}$ per one-hour step give 190 and
340\,W\,m$^{-2}$; \code{lsp+cp} $=1.13\times10^{-4}$\,m/step gives
$3.14\times10^{-5}$\,kg\,m$^{-2}$\,s$^{-1}$. All correct global means, so a jinja-gated
\code{file\_def} block would have delivered the forward direction with no new component.

Decided against it. XIOS solves the forward direction only: it cannot deliver \code{plit} into the
live atmosphere, and cannot route basal melt and discharge into the ocean. Both need a component
inside the OASIS exchange, and one mechanism is better than two. Staying on the EC-Earth component
also keeps CISSEMBEL available.

Also decided: carry both SMB schemes with dEBM as default; SMB before orography; everything behind
\code{general.smb\_coupled}.

\subsection{The ISM-mapper becomes an esm\_tools component (2026-08-03)}

\code{configs/components/ismm/ismm.yaml}, in the \code{develop-is} coupling, always built.

It is not a standalone repository: it lives inside \code{ecearth4} under
\code{sources/ism-mapper}, so the component clones ecearth4 and builds that subtree. The clone is
37\,MB, not the 663\,MB the local \code{.git} suggests, because every \code{sources/*} model is a
submodule that is not recursed into. The branch \code{cissembel-levante-intel} is required rather
than preferred: it carries \code{5799a2a}, which fixes an \code{EBMfinalize} use-after-free that
crashes any run with a non-CISSEMBEL region.

CISSEMBEL is a \emph{link-time} dependency even on the direct path
(\code{ism-mapper\_run\_mod.F90:7} has an unguarded \code{use modEBMworld}), so it is built from
the same clone. At runtime \code{EBMworld} only fires for regions with
\code{ISMRGNCIS(n)=.true.}, so it never executes for us.

The committed \code{Makefile} carries ECMWF HPC2020 paths. Everything it needs is a plain make
variable and command-line macros beat file assignments, so the machine configuration is passed in
\code{comp\_command} rather than by patching a tracked file.

\medskip\noindent
\textbf{Verified.} Built end to end from a fresh clone. The open risk was whether code written
against OASIS 5.2 links against our 5.0-smhi; it does, with no source change. The binary carries
\code{oasis\_init\_comp}, \code{oasis\_def\_var}, \code{oasis\_enddef}, \code{ebmworld} and
\code{ebminitialize}.

\subsection{The PISM grid goes into ocp-tool (2026-08-03)}
\label{sec:grid}

The ISM-mapper is an OASIS component, so the PISM domain must appear in
\code{grids.nc}/\code{masks.nc}/\code{areas.nc}. This went into ocp-tool, not esm\_tools: ocp-tool
already sits between PISM and AWI-ESM3, it is where the weight generation lives, and
\code{ocp\_tool/grids/} already has the abstraction (a class with \code{cell\_latitudes},
\code{cell\_longitudes}, \code{cell\_corners}, \code{cell\_areas}, \code{cell\_masks}). Putting it
there deleted a planned step: ocp-tool writes \code{ismp} itself, so nothing appends fragments
afterwards.

Centres come from the PISM file's own \code{lat}/\code{lon}; corners are inverse-projected from the
cell corner $(x,y)$; areas are spherical excess over two triangles.

\medskip\noindent
\textbf{Verified} on \code{antarct\_cr} 8\,km, $761\times761$, three ways, because a wrong grid
fails as silently-bad weights rather than a crash:
\begin{itemize}
\item Area total 36.03 against 36.28\,$\times10^6$\,km$^2$ from the plane area corrected by the
      polar stereographic scale factor, $-0.70\%$.
\item Cell areas 67.0\,km$^2$ at the pole to 53.8 at the outer corner against a nominal 64, the
      right sign and size for \code{lat\_ts}$=-71$.
\item All 579121 cells wind counterclockwise seen from outside the sphere, no sign flips. SCRIP
      requires this and the area check cannot detect it.
\end{itemize}
A full TCO95/CORE3 run puts \code{ismp} in all three files, bit-identical to an independently
generated reference.

\medskip\noindent
\textbf{Found on the way:} ocp-tool was appending the FESOM grid unconditionally. FESOM writes its
own \code{feom} entry at runtime in domain-decomposition order; ocp-tool's is mesh order, and the
two disagree. Now behind \code{ocean.write\_oasis\_grid}, default off. \emph{This changes default
output for every FESOM config, not only ours.}

\subsection{Declaring the OASIS coupling (2026-08-03)}

Field names on the ice side come from the ism-mapper itself
(\code{cplng\_config\_mod.F90}): \code{<prefix>\_Precip\_liquid}, \code{\_Precip\_solid},
\code{\_Evaporation}, \code{\_Runoff}, \code{\_Soil4T}, \code{\_SST} inbound and
\code{<prefix>\_plit} out. On the OIFS side \code{A\_Evap\_ISM}, \code{A\_SST\_ISM} and
\code{A\_Soil4T\_ISM} are what \code{ecearth.F90} declares for the direct path; precip and runoff
are reused from the ocean path.

Two constraints the parser caught, both of which would have been expensive later:
\begin{itemize}
\item \code{A\_Runoff} is on \code{atmr}, not \code{atma}, so it needs its own exchange line and
      its own direction. Grouping it with precip fails the same-grid validation.
\item \code{include\_models} is consumed before general-level \code{choose\_} blocks resolve, so
      \code{ismm} must sit in the \code{develop-is} \code{add\_include\_models}. It moves together
      with \code{smb\_coupled}: a launched \code{ismm} with no coupled fields deadlocks OASIS.
\end{itemize}

\subsection{Generating the weights (2026-08-03)}
\label{sec:weights}

Weights are not left to OASIS at model runtime. \code{ocp\_tool/oasis\_weights.py} precomputes
them with pyOASIS taken from the coupled model's own OASIS build, ported from rdy2cpl: one MPI
rank per link, each calling \code{enddef()} so SCRIP writes that link's \code{rmp\_*.nc}. Geometry
is read back from the OASIS description files, so the \code{ismp} entry of \S\ref{sec:grid} is
exactly what a link consumes. It needs compute nodes; the one-rank-per-link parallelism is what
makes it tractable.

Tested on 3 nodes against ocp-tool's own TCO95/CORE3 output:

\begin{center}
\begin{tabular}{@{}llr@{}}
\toprule
link & map & result \\
\midrule
\code{A096 $\to$ ismp} & \code{BILINEAR D}  & 69\,MB \\
\code{R096 $\to$ ismp} & \code{GAUSWGT D}   & 122\,MB \\
\code{ismp $\to$ A096} & \code{GAUSWGT LR}  & 44\,MB \\
\code{ismp $\to$ A096} & \code{DISTWGT LR}  & 34\,MB \\
\code{ismp $\to$ A096} & \code{BILINEAR}    & OASIS abort, rc=1 \\
\code{ismp $\to$ A096} & \code{CONSERV}     & OASIS abort, rc=1 \\
\bottomrule
\end{tabular}
\end{center}

\noindent
\textbf{Why the ice$\to$atm conservative and bilinear maps die.} 381 of the 579121 cells have a
corner longitude spread above $180^\circ$ along the polar seam, and the pole cell's four corners
sit at $-135, 135, 45, -45$, encircling the pole outright. That breaks SCRIP's per-cell longitude
line integral (CONSERV) and its enclosing-quadrilateral search (BILINEAR). Neighbour-based maps do
not care. Same geometry as the reason the areas use spherical excess.

\medskip\noindent
\textbf{Consequence.} \code{plit} reaches \code{suorog} as an interpolated value, not the area
fraction \code{ECE\_LANDICE\_THRESH} is written to read. EC-Earth's bilinear would give the same,
so we are no worse than the reference, but the threshold semantics are looser than ideal.

\begin{itemize}

\item \code{ismp} grid written by ocp-tool into all three OASIS files, geometry verified three

\item All three coupling links generate on compute (\S\ref{sec:weights}).
\item The esm\_tools config assembles: \code{ismm} in \code{process\_ordering}, \code{rstism.nc}

\end{itemize}

\subsection{Open}

\begin{itemize}
\item \textbf{Nothing has run coupled.} No leg has been launched with \code{ismm} in it.
\item \textbf{\code{ECE\_CPL\_ISMM} not yet set.} It belongs in the runscript next to
      \code{ECE\_LANDICE}/\code{ISMRGNPFX}; \code{NAMECECFG} is \code{add\_}'d per chunk there and
      a second \code{add\_} from the setup collides.
\item \textbf{PISM links not wired into \code{regenerate\_oasis\_weights}}, which still defaults to
      the feom set. Also \code{nlinks} there defaults to 4 while \code{awiesm3\_feom\_links()}
      returns 5, so one link already serialises; PISM takes it to 8.
\item \textbf{Per-leg \code{namelist.ismm}} and the \code{cpl\_dir/\{aux,prev\_year\}} staging.
\item \textbf{Consume the SMB:} turn \code{\{region\}\_smb\_\{year\}.nc} into
      \code{atmosphere\_file\_for\_ice.nc}, replacing the stub of \S\ref{sec:taint}.
\item \textbf{\code{orog} for the downscaling reference.} \code{field\_def.xml:176} has a \code{z}
      but it is in the \code{3D\_ml} group, so model-level geopotential. Source it from the ICMGG
      with eccodes for param 129, as \code{make\_plit\_oifs.py} does for \code{lsm}.
\item \textbf{\code{usurf\_oifs} writer} and replacing the ICMGG-derived \code{plit} with PISM's
      own mask.
\item \textbf{Freshwater return.} PISM basal melt and discharge do not reach FESOM. Not needed for
      SMB or orography, but it is the remaining leg of the mass budget.
\item \textbf{atlas 0.31.1 $\to$ 0.39.0} came in with the vendor merge and is unbuilt.
\end{itemize}

\noindent
The \code{-huge} trap is worth stating once in full: receive buffers are initialised to
\code{-huge}, \code{AccumulateECEForcingFields} adds every \code{OASIS\_IN} field with no check
that it is coupled, and an uncoupled field is never written. So a declared-but-unpartnered input
accumulates \code{-huge} for a whole leg. This is the same failure class as the OIFS-side
\code{-HUGE} first-send bug, arriving from the other end.

\subsection{Falsified claims (kept, struck through)}
\label{sec:falsified}

\begin{itemize}
\item \dead{Adding a PISM grid means teaching the per-leg regeneration to emit SCRIP weights to
      and from TCO95 on every cycle. This is the expensive part and the main schedule risk.}
      Overstated: the weight machinery is general, so PISM costs a few \code{Link} entries.
\item \dead{OASIS computes the weights itself at runtime, and the PISM grid does not move, so
      there is no per-cycle work.} Wrong twice. Weights are precomputed via pyOASIS
      (\S\ref{sec:weights}), and the links do regenerate per mesh-change leg because the OIFS mask
      moves where PISM is.
\item \dead{CONSERV is the right map for plit, since ECE\_LANDICE\_THRESH reads an area fraction.}
      It aborts on a pole-centred grid (\S\ref{sec:weights}). GAUSWGT is what works.
\item \dead{The ice$\to$atm link is \code{BILINEAR D}.} The SCRIPR letter is the \emph{source}
      grid type and \code{ismp} is logically rectangular, so \code{LR}; and \code{BILINEAR} fails
      here regardless.
\end{itemize}

\subsection{Method notes}

\begin{itemize}
\item \code{esm\_runscripts -c} assembles the full runtime config and catches grid-consistency and
      component-loading errors. Both config bugs above were found this way, not by reading.
\item \code{esm\_master --check <target>} renders the build without executing it. It also revealed
      the pre-existing \code{debm} section-header failure.
\item Weight generation must run from a shared filesystem. A first attempt with the working
      directory on \code{/tmp} died in 14\,s: \code{/tmp} is node-local on Levante, so the compute
      node could not write the job output.
\item Grid winding is invisible to an area check, which takes an absolute value. Test it
      separately by dotting the corner-polygon normal with the outward radial vector.
\end{itemize}
